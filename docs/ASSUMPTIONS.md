| A35 | Comunicação (templates/canais) | Templates + opt-in + CRUD MessagingChannel + envio manual. EMAIL=SMTP; WHATSAPP=Evolution real se `EVOLUTION_MOCK=false` + baseUrl/apiKey/instance (env, canal ou IntegrationConnection); senão FAILED (nunca SENT falso). Canal WhatsApp novo exige `integrationConnectionId` (Evolution/Chatwoot ativa com credenciais, mesma organização); o envio usa essa conexão e marca FAILED se ela deixar de estar conectada. Canais antigos sem vínculo mantêm o fallback por clínica. SMS ainda stub. Lembretes/confirmações automáticos usam o texto do modelo ativo (ver A52/A53) |
| A36 | Áudio/transcrição | Explicitamente fora de escopo do backlog QA |
| A37 | Merge de pacientes | Origem → destino; move vínculos clínicos/financeiros; origem vira ARCHIVED; ClinicalRecord por clínica é consolidado; pastas com mesmo nome são unificadas. UI: Configurações → Pacientes duplicados (inclui `SAME_NAME` para duplicados de importação Nibo) |
| A38 | Google Calendar OAuth | **Fatia 4 + remessa P2 + gap 2026-09 + 1.3.8–1.3.13:** OAuth real estilo N8N — Client ID/Secret na UI (conexão criptografada), env `GOOGLE_CLIENT_*` opcional como fallback. **Redirect 1.3.13:** a UI calcula `${NEXT_PUBLIC_API_URL}/integrations/google/callback`, exibe para copiar no Google Cloud Console e envia `redirectUri` no save e no `oauth/start` (persistido na conexão). Ordem na API: conexão → body → `GOOGLE_REDIRECT_URI` → derivado de `API_URL`. **Não** exige `API_URL` no Swarm só para OAuth se o web já aponta para a API correta. Validação anti open-redirect (HTTPS + sufixo `/integrations/google/callback`). **UX 1.3.12+:** “Conectar / Autenticar” navega na **mesma aba** (`location.assign(authorizeUrl)`); callback redireciona ao app. Sync clinic→Google (outbox); Google→clinic via pull-sync **e** webhook se `GOOGLE_CALENDAR_WEBHOOK_URL`. Pull-sync conta eventos pessoais (overlay) e falhas (MOCK/OAuth) na API/UI. Auto-renew no worker se `GOOGLE_CALENDAR_WATCH_AUTO_RENEW=true`. Produção: `GOOGLE_CALENDAR_MOCK` ausente ou false (fail-fast só recusa `true`); OAuth na UI — **GO só com OAuth concluído**. Parse: só `true/1/yes` liga; `false/0/no` desliga; ausência em prod = off. oauth-status expõe `mock` + `mockEnvPresent`. Swarm defaulta MOCK=false; `deploy.sh` recusa MOCK ligado |

| A39 | Retornos `allowedHours` | Formato `{ start, end, weekdays, timezone? }` (default TZ `America/Cuiaba`). `{}` = 24/7. Se **todas** as regras matching estão fora da janela, o outbox adia com `leaseUntil` sem consumir attempts. Se há regras dueNow + deferred, só dueNow rodam e o evento é marcado processado (deferred daquele evento não reexecutam) |
| A40 | Financeiro líquido | `paidAmount`/`outstandingAmount` vêm da API (`buildReceivableFinanceView`); front não recalcula regra. OVERDUE é efetivo se saldo > 0 e `dueDate < hoje` |
| A41 | Tarefas recorrentes | Idempotência via `Task.occurrenceKey`; worker + `POST /tasks/:id/recurrence/generate` |
| A42 | Escopo profissional | Tabelas `ProfessionalClinic`/`Unit`/`Specialty`. Com `clinicId`, listagens/filtros **exigem** vínculo ativo (sem fallback “sem links”). Migration Fatia 3 backfill + seed criam vínculos |
| A43 | Duplicados de paciente | `PatientDuplicateDismissal` persiste “não são duplicados”; merge só via Configurações com preview de conflitos |
| A44 | Evolução DRAFT | Exclusão é **hard delete** (`DELETE /clinical-entries/:id`) com auditoria `clinical.draft_deleted` |
| A45 | Calendar event mapping | `Appointment.externalCalendarEventId` guarda o id do evento Google; cancelamento remove o evento quando OAuth ativo |
| A46 | Anamnese multi-tenant | Escopo **global na organização**: `clinicId` deve ∈ org; não exige `PatientClinic`. Hash canônico inclui `clinicId`/`patientId`/`templateId`/`templateVersion`/answers (breaking, só dev) |
| A47 | Anamnese lifecycle | `AWAITING_SIGNATURE` é imutável (409). Reopen só sem assinaturas. Assinada: cancelar (`CANCELLED` + motivo) **ou** criar atualização (`sourceResponseId`, origem permanece SIGNED/EXPIRED). Origem só vira `SUPERSEDED` na finalização da nova versão (concorrência → 409). `EXPIRED` materializado no worker + `effectiveStatus` |
| A48 | Produção vs recebimento | `production-procedure` = produção clínica (`item.total / plannedSessions`, sessões `completedAt`, sem correções). `receipt-procedure` = recebimentos líquidos alocados às sessões elegíveis. Profissional usa a mesma base clínica |
| A49 | Release / prod bootstrap | Tag `vX.Y.Z` dispara CI + imagens + deploy Swarm. **1.3.10+:** `prisma migrate deploy` no boot de **api e worker** (`runBootMigrations`, advisory lock, verificação de colunas críticas, fail-fast); serviço Swarm `migrate` opcional (CREATE DATABASE + pré-deploy). Setup inicial em `/setup` (operador informa o token; API exige `X-Setup-Token`). API/worker recusam startup inválido. Swagger off por default em prod. Readiness em `/api/v1/health/ready` (Traefik). `WEB_URL` canônico (HTTPS). Imagens do stack sem fallback `1.0.0`. |
| A50 | Nibo ↔ Financeiro | **Pull:** import manual `POST /integrations/nibo/:id/import` (alias legado `POST /integrations/:id/nibo/import`) **e** pull periódico do worker (`finance.nibo-pull.requested`, intervalo `NIBO_PULL_INTERVAL_MS`, default 30min) — create **e update** por `externalId` (cancelados locais preservados). **Paciente:** match por CPF; senão por nome exato; senão cria paciente do contato Nibo; fallback “Importação Nibo (sem paciente)” só sem nome/documento. Descrição: `contato — descrição`. **Pago:** schedules PAID/parcial geram `Payment` / `PayablePayment` (idempotente) para o fluxo de caixa. **Filtros:** categorias de recebíveis → só crédito; categorias de pagáveis → só débito (vazio = todas as despesas); centros de custo → só débito — sem CC selecionado importa todos os débitos; com CC selecionado só itens desses centros (despesa **sem** centro no Nibo fica de fora). Recorrências (`hasRecurrence`/`isRecurrent`) viram `FinanceRecurrence` com `generateLocally=false` (parcelas vêm do pull, sem duplicar). IDs case-insensitive. Worker loga tick/skip/complete. **Push:** outbox `finance.nibo-sync.requested` em create/update Receivable, create Payable, baixa (PAY) Receivable/Payable e cancel Payable (DELETE schedule). Worker: schedule credit/debit + receipts/payments + DELETE. **Contas bancárias:** UI multiselect (`accountIds`/`niboAccountIds` + `accountNames`); mantém `accountId`/`niboAccountId` = primeira da lista (compat). Baixa Nibo aceita **uma** conta por lançamento — não espalha em N contas; usa conta do título/payload quando houver, senão a primeira da integração. Sem estorno de baixa no Nibo. Produção: `NIBO_MOCK=false` (fail-fast + deploy.sh). UI integrações: lista só ACTIVE/ERROR; botão Adicionar para provedores disponíveis; catálogo Nibo persiste nomes junto dos IDs |
| A51 | Paciente → Google Calendar | No cadastro de paciente, outbox `patient.calendar-sync.requested` cria evento **all-day** no dia do cadastro (TZ da unidade) se Google ACTIVE + OAuth + `GOOGLE_CALENDAR_MOCK=false`. Persiste `Patient.externalCalendarEventId`. Soft-fail: create do paciente não quebra se calendário falhar |
| A52 | Régua de lembrete/confirmação | A régua mora no **modelo de mensagem** (`MessageTemplate.schedule` JSON: `leadMinutes` 15–10080; `mondaySendDay` `FRIDAY`\|`SUNDAY`, só Lembrete). O envio automático usa o **1º modelo ativo da categoria por nome**. Agendamento com lembrete ligado: antecedência escolhida na agenda (override) ou a do modelo de Lembrete (padrão 24h); se houver modelo de Confirmação ativo, cria também `AppointmentReminder` com canal `WHATSAPP:CONFIRMATION`. **Consulta na segunda:** envio que cairia no sábado/domingo vai para a sexta anterior (padrão) ou fica no domingo (`applyMondaySendDay`, TZ da unidade). Retorno não tem régua no modelo — usa “Retornos automáticos”. Placeholders compartilhados em `@sonder/database` (`messaging-rules.ts`): `patientName`, `date`, `appointmentTime`, `clinicName`, `clinicAddress` (`Unit.address` → nome da unidade · cidade), `professionalName` |
| A53 | Respostas WhatsApp (confirmar/cancelar) | `POST /integrations/whatsapp/webhook/:connectionId?token=` (sem AuthGuard; token HMAC-SHA256 da `ENCRYPTION_MASTER_KEY` por conexão; rate limit de webhook; dedup em `WebhookReceipt`). Evolution `messages.upsert` (ignora `fromMe` e grupos) / Chatwoot `message_created` incoming. Resposta curta (≤3 palavras): SIM/S/CONFIRMAR/CONFIRMO/1 → `CONFIRMED`; NÃO/N/CANCELAR/DESMARCAR/2 → `CANCELLED` (+ remoção do evento Google e lembretes pendentes desativados). Alvo: próxima consulta futura (SCHEDULED/CONFIRMED) da clínica da conexão cujo paciente tem o mesmo celular e recebeu lembrete WhatsApp (SENT) nos últimos 7 dias. Registra `AppointmentStatusEvent` (`PATIENT_WHATSAPP`) + `AuditEvent`. **Nunca** envia resposta automática. URL exibida em Configurações → Integrações → Ver |
| A54 | Compromissos na agenda | `Appointment.kind` = `APPOINTMENT` (consulta, exige paciente) ou `COMMITMENT` (reunião, almoço, manutenção: exige `title`, sem paciente). CHECK `appointment_kind_patient_title` garante a regra no banco; compromissos ocupam o horário do profissional/cadeira (mesmas exclusion constraints de overlap). Ficam fora de lembretes/confirmações, relatórios de atendimento, dashboard, busca de pacientes e da API pública (que só lista/cria consultas). No Google Calendar o evento usa o título do compromisso |
| A55 | Lembrete WhatsApp sem integração ativa | Sem Evolution/Chatwoot `ACTIVE` na clínica da consulta, o `AppointmentReminder` é gravado `DISABLED` com `statusReason` = `WHATSAPP_NOT_CONFIGURED_REASON` (`messaging-rules.ts`). Teste de conexão com sucesso, salvar credenciais ou reativar Evolution/Chatwoot devolve à fila (`PENDING` + outbox) só lembretes futuros com esse motivo, da mesma organização/clínica, de consulta com paciente não encerrada (até 1000 por vez); falha nessa etapa não desfaz a ativação. Salvar a consulta também reavalia. A agenda mostra o motivo real do bloqueio |
| A56 | Lembrete WhatsApp enviado uma vez só | Worker faz claim atômico `PENDING`/`FAILED` → `SENDING` antes de enviar; evento duplicado do mesmo lembrete (reativação repetida, réplicas) é descartado. Queda no meio do envio deixa `SENDING` e não reenvia (preferimos perder um lembrete a duplicar). Editar a consulta sem mudar horário nem antecedência mantém os lembretes `SENT`/`SENDING` (não reenvia e a resposta SIM/NÃO continua achando a consulta); remarcar o horário ou mudar a antecedência gera envio novo. Integração desativada continua listada em Configurações → Integrações com “Reativar” (credenciais preservadas) |
| A57 | Google do profissional, cadeira e procedimentos | Consulta sincroniza só na conta Google do profissional (`scopeId` = professionalId); sem conta própria, usa a conexão da clínica e não copia para a agenda pessoal de colega. Cadeira ocupada (SCHEDULED/CONFIRMED/CHECKED_IN/IN_PROGRESS) recusa outro atendimento no mesmo horário, também na importação. O select de procedimento no novo tratamento lista o catálogo por nome, código e TUSS |
| A58 | Catálogo, modal, relatórios e antecedência | A primeira listagem de procedimentos grava o catálogo padrão da organização, sem duplicar os já existentes. O título "Plano de tratamento" vale só na criação. O modal de criar consulta ou compromisso fecha ao salvar. Relatórios seguem as colunas da tela. Criar consulta oferece antecedência de 2 horas, 1 dia ou 2 dias |
